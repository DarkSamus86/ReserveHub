# Логи микросервисов ReserveHub

Каждый микросервис пишет одну JSON-запись на строку в stdout. Docker Compose собирает поток контейнера и ограничивает размер локального хранения. Общий формат позволяет искать записи всех сервисов по одинаковым полям и в дальнейшем подключить центральное хранилище без изменения бизнес-кода.

## Поля

| Поле | Смысл |
| --- | --- |
| `timestamp` | Время записи, UTC, RFC 3339. |
| `level` | `DEBUG`, `INFO`, `WARN` или `ERROR`. |
| `message` | Короткое стабильное имя события, например `grpc_request`. |
| `service` | Имя микросервиса, например `tenant-service`. |
| `environment` | Окружение из `APP_ENV`, по умолчанию `local`. |
| `request_id` | Идентификатор запроса из входящего `x-request-id` либо созданный сервисом UUID. Возвращается в gRPC заголовке `x-request-id`. |
| `trace_id`, `span_id` | Идентификаторы активного OpenTelemetry span, если он есть. |
| `tenant_id` | Tenant запроса, когда он указан в gRPC сообщении. |
| `grpc_method`, `grpc_code`, `duration_ms` | Метод, итоговый код и длительность gRPC вызова. |
| `error` | Ошибка фоновой операции, когда она действительно есть. |

Все поля, кроме первых пяти, добавляются только по контексту. Не записывайте полные gRPC тела, секреты и токены. Для ошибок gRPC указывайте код в `grpc_code`; `WARN` используется для ожидаемых отказов, `ERROR` для внутренних ошибок и недоступности зависимостей.

## Локальный просмотр

```bash
docker compose logs -f tenant-service
docker compose logs -f
```

Первый вызов показывает один сервис, второй — все контейнеры проекта. `LOG_LEVEL` управляет уровнем приложения, `APP_ENV` задаёт окружение. В Compose для микросервисов применяется ротация Docker логов: до пяти файлов по 10 МБ на контейнер.

Новые Go сервисы должны использовать этот же набор полей, писать JSON в stdout и добавлять `request_id` и идентификаторы трассировки к входящим запросам. Имя сервиса должно совпадать с его именем в Compose и в ресурсе OpenTelemetry.
