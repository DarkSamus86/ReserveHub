# Логирование микросервисов ReserveHub

Все микросервисы ReserveHub используют единый структурированный формат: **одна JSON-запись на строку в stdout**. Docker Compose собирает stdout/stderr контейнеров и ограничивает локальное хранение логов. Совместимый формат позволяет искать записи разных сервисов одинаковым способом и подключить централизованное хранилище без изменения бизнес-кода.

## Общая схема записи

```json
{"timestamp":"2026-10-23T12:00:00Z","level":"INFO","message":"http_request","service":"auth-service","environment":"local","request_id":"req-123","http_method":"POST","http_route":"POST /v1/auth/login","http_status":200,"duration_ms":8.4}
```

## Стандартные поля

| Поле | Смысл |
| --- | --- |
| `timestamp` | Время записи в UTC, RFC 3339. |
| `level` | `DEBUG`, `INFO`, `WARN` или `ERROR`. |
| `message` | Короткое стабильное имя события в `snake_case`, например `http_request`, `grpc_request`, `bootstrap_admin_ready`. |
| `service` | Имя микросервиса; должно совпадать с именем сервиса в Compose, например `auth-service`. |
| `environment` | Окружение из `APP_ENV`, по умолчанию `local`. |
| `request_id` | Входящий `X-Request-ID`/`x-request-id` или сгенерированный UUID. Сервис возвращает ID в ответном HTTP/gRPC заголовке. |
| `trace_id`, `span_id` | Идентификаторы активного OpenTelemetry span, если трассировка доступна. |
| `tenant_id` | Tenant запроса, только если он надёжно определён из проверенного контекста. |
| `user_id` | Идентификатор пользователя только если он нужен для аудита и его запись разрешена политикой приватности. |
| `duration_ms` | Длительность HTTP/gRPC запроса либо фоновой операции в миллисекундах. |
| `error` | Безопасное описание ошибки фоновой операции или сбоя; не включать секреты и credentials. |

## Поля HTTP и gRPC запросов

Для HTTP-запросов микросервис пишет:

- `http_method` — HTTP-метод;
- `http_route` — шаблон маршрута, например `POST /v1/auth/login`; не полный URL с query-параметрами и пользовательскими значениями;
- `http_status` — код HTTP-ответа;
- `request_id`, `duration_ms`.

Для gRPC-запросов микросервис пишет:

- `grpc_method` — полное имя метода;
- `grpc_code` — итоговый gRPC status code;
- `request_id`, `duration_ms`;
- `tenant_id`, `trace_id`, `span_id`, если они достоверно известны.

Названия транспортных полей могут отличаться, но пять базовых полей (`timestamp`, `level`, `message`, `service`, `environment`) и правила уровней/безопасности должны быть общими.

## Уровни логирования

- `INFO` — успешные запросы и ожидаемые lifecycle-события;
- `WARN` — ожидаемые отказы/валидационные ошибки, например неуспешная аутентификация или недостаточные права;
- `ERROR` — внутренние ошибки сервиса, недоступность зависимостей и сбои фоновых операций;
- `DEBUG` — диагностические детали без персональных данных и секретов; по умолчанию выключен.

Уровень задаётся через `LOG_LEVEL`; окружение — через `APP_ENV`. Имена событий должны быть стабильными и пригодными для фильтрации, не следует подставлять динамический текст ошибки в `message`.

## Требования безопасности

Запрещено логировать:

- пароли, password hashes, access/refresh tokens, cookies, JWT signing secrets;
- полные тела запросов/ответов аутентификации и платежей;
- секреты, ключи, платёжные данные и другие credentials;
- URL с query-параметрами, если там могут быть персональные данные или токены.

В частности, `auth-service` может логировать маршрут, HTTP-статус, request ID и длительность login/register, но не email, пароль или bearer token. Для аудита административных действий используется отдельная контролируемая запись с actor/resource ID только при наличии соответствующего основания.

## Локальный просмотр

```bash
docker compose logs -f auth-service
docker compose logs -f tenant-service
docker compose logs -f
```

Первый/второй вызов показывают отдельный сервис, последний — все контейнеры проекта. В Compose для микросервисов включена ротация Docker logs: до пяти файлов по 10 МБ на контейнер.

## Требования к новым сервисам

Новый микросервис обязан:

1. использовать JSON logger, совместимый с общей схемой;
2. писать записи в stdout и не менять стандартные имена базовых полей;
3. принимать `X-Request-ID`/`x-request-id`, проверять/ограничивать его формат, генерировать UUID при отсутствии/некорректном значении и возвращать ID в ответе;
4. логировать стабильное имя HTTP route template или gRPC метода, статус и длительность;
5. не писать секреты и полные тела запросов;
6. использовать одинаковые правила `LOG_LEVEL`, `APP_ENV` и уровней логирования;
7. иметь тесты, проверяющие JSON schema, request ID и отсутствие credentials в логе.
