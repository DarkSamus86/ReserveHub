# Auth Service: план развития БД

**Состояние:** предложения для текущей ветки `dev`, 2026-10-23; миграции и код этим документом не меняются.
**Основание:** [требования Auth](../../services/auth-service/ReserveHub-Auth-Service-STPO.md), [регресс QA](../../qa/test-results-2026-10-23-regression.md), [security review](../../security/backend-security-report.md), миграции `services/auth-service/migrations/000001–000002` и `internal/repository/postgres.go`. Бизнес-инварианты сверены с `analyst`.

## Граница данных и текущее состояние

`auth-service` владеет глобальными пользователями, учётными данными, platform-ролями, tenant-ролями, членствами, приглашениями и учётными сессиями. `tenant-service` владеет существованием и состоянием tenant. Пароль и identity не копируются в его БД; межсервисного FK к tenant нет.

Сейчас обе схемы находятся в одном PostgreSQL database `reservehub`; физическое разделение на отдельные DB/кластеры можно рассмотреть позже. На текущем этапе нужны отдельные runtime/migration роли и отсутствие межсхемных FK/JOIN, чтобы контракт продолжил работать после возможного разделения.

Сейчас `auth_service.users` содержит `email`, `password_hash`, `role_id`; `roles` имеет `scope`, `tenant_id`, уникальные коды в пределах scope. Публичная регистрация выбирает platform `user`, а bootstrap — platform `admin` через фильтр в запросе. **Подтверждённый пробел схемы:** `fk_users_role` проверяет только существование `roles.id`. Прямое назначение tenant-scoped `admin` в `users.role_id` допустимо. Исправленный JWT `scope` закрывает прежний обход в `tenant-service`, но инвариант identity остаётся нарушенным. Таблиц membership, invitation, session и аудита пока нет.

## Что делать сейчас

1. **P0: зафиксировать platform scope для `users.role_id` в БД.** Сначала прочитать все строки `users JOIN roles`, где `roles.scope <> 'platform'` или `roles.tenant_id IS NOT NULL`, сохранить идентификаторы и основание исправления в защищённом журнале миграции. Такие строки нельзя автоматически повышать до platform `admin`. Исправление каждой требует явного решения: вернуть проверенную глобальную роль `user` либо изолировать аккаунт до разбирательства. Миграция должна прекращаться при необработанных строках.
2. Добавить в `users` постоянный маркер `role_scope = 'platform'` с `NOT NULL` и `CHECK`, уникальный ключ `roles(id, scope)` и составной FK `users(role_id, role_scope) → roles(id, scope)`. Старый FK можно удалить после проверки нового. Для действующей таблицы: предварительный аудит → расширение схемы → backfill/валидация → `NOT NULL`/FK validation → переход приложения. `NOT VALID`/`VALIDATE CONSTRAINT` допустимы для снижения длительной блокировки, но блокировки DDL и объём таблиц надо проверить на копии данных. Альтернатива — отдельный каталог platform-ролей и FK на него; не выбирать оба варианта одновременно.
3. Укрепить уникальность email в БД по той же нормализации, что применяет приложение. Сейчас `UNIQUE(email)` чувствителен к регистру, а Go приводит адрес к lower-case. Для будущих импортов/ручных операций нужна проверка `email = lower(btrim(email))`, длины и уникальный индекс `lower(email)` после аудита коллизий. Не менять семантику email без согласования с владельцем API. Парольный хэш хранить только в auth-схеме; никаких паролей/токенов в аудит и outbox.
4. Разделить учётные данные БД: отдельные runtime и migration роли для `auth_service`, запретить runtime DDL и доступ к `tenant_service`. Bootstrap job должен пользоваться ограниченной ролью auth, а не общим суперпользователем. Закрыть внешний доступ к PostgreSQL; в недоверенной сети включить проверяемый TLS. `search_path` в Compose сейчас задаёт схему, но **сам по себе не ограничивает права**. Проверить `USAGE`/DML на текущих и будущих таблицах, sequences и default privileges; удостовериться, что `public` не даёт лишних прав.

## Следующий этап: owner и membership

Перед внедрением согласовать контракт с `backend-security`: какая команда и какой проверенный actor запускают provision, как выражены состояния приглашения, какое окно отзыва допускается, и какие таблицы обновляются одной auth-транзакцией.

Предлагаемая модель:

| Данные | Ключи и ограничения | Смысл |
| --- | --- | --- |
| `users` | `id`, нормализованный уникальный `email`, platform-only `role_id`, статус | Одна глобальная identity; `INVITED`/`SUSPENDED` не получают access token. Переходы статусов задаёт бизнес-правило. |
| `roles` | `scope`, `tenant_id`, `code`; дополнительно уникальный `tenant_id` для tenant scope | Одна tenant-scoped роль на tenant, код фиксируется при создании; `admin` как code/имя tenant не даёт platform прав. |
| `tenant_memberships` | `id`, `user_id` FK, `tenant_id`, `tenant_role_id`, `permission_profile`, `status`, timestamps; `UNIQUE(user_id, tenant_id)` для текущего членства | Один user может иметь много tenant; активное подтверждённое членство и профиль прав нужны одновременно. Составной FK `(tenant_role_id, tenant_id)` на уникальные `roles(id, tenant_id)` должен гарантировать принадлежность роли тому же tenant; все три поля обязательны. |
| `invitations` | `id`, `tenant_id`, `email`, `token_hash`, `expires_at`, `accepted_at`, `revoked_at`, idempotency key | Существующий email получает доступ только после принятия приглашения либо через подтверждённую сессию. Хранить только hash одноразового секрета. |
| `provision_requests` | уникальный ключ исходной операции/tenant, состояние, попытки, последняя безопасная ошибка | Повторный вызов не создаёт вторую роль, user или membership; сбой виден и допускает retry. |

Создание роли, приглашения, предварительного membership и результата provision должно быть одной auth-транзакцией. `tenant_id` передаётся из доверенного оркестратора и проверяется по межсервисному контракту; локальный FK к чужой БД не нужен. При удалении или архивации tenant требуется отдельная доставка события и согласованная реакция членств. Для изоляции запрос всегда связывает `user_id`, выбранный `tenant_id`, статус membership и profile; role code или JWT `tenant_id` без проверки недостаточны. Уникальный `(user_id, tenant_id)` обслужит точечную проверку доступа; индекс для списка пользователей tenant добавлять после появления запроса и оценки плана. PostgreSQL RLS можно оценить позже: нынешний общий пул соединений не передаёт надёжный tenant context в каждую транзакцию, поэтому объявлять RLS защитой сейчас нельзя.

Есть **несовпадение контрактов**: `tenant.slug` допускает 100 символов и может начинаться с цифры, а `roles.code` — максимум 63 и должен начинаться с буквы. До owner provisioning согласовать один предел и алфавит для slug/role code либо явное стабильное отображение. Проверить существующие slug перед ограничивающей миграцией.

Сессии, отзыв refresh token, блокировка, аудит выдачи/отзыва членства и админских изменений — отдельные таблицы/миграции следующего этапа. Для refresh/invite/reset хранить только хэш секрета, срок действия и факт использования; сроки хранения identity и аудита пока требуют решения продукта и правового анализа. Для access JWT решить, как быстро отражать отозванные права: короткий TTL, версия прав/сессии либо online-check. БД одна этого не обеспечивает.

## Ввод без потери данных и приёмка

- Новые миграции добавлять по порядку после `000002`; текущие миграции не переписывать. Перед ограничениями запускать read-only аудит ролей и email-коллизий на копии, сохранить backup и план восстановления. Развёртывание делать через expand → обновление кода → validation/contract; старый auth должен понимать новые nullable поля до переключения. Откат ограничения возможен отдельной миграцией; потерянные/переназначенные identity автоматическим down не восстанавливаются.
- Отдельные DB roles и grants внедрять после проверки всех запросов auth, bootstrap и migrator на тестовой БД; migration role не использовать в runtime. Проверить реальный `current_user`, schema/table privileges и отказ cross-schema чтения/записи.
- Приёмка: публичный user получает только platform `user`; SQL попытка привязать tenant-role к `users.role_id` отклоняется; tenant `admin` не становится platform admin; membership tenant A не даёт доступа B; pending/revoked приглашение не даёт прав; повторный provision идемпотентен; существующий email ждёт подтверждения; сбой provision остаётся видимым для retry.

## Открытые решения продукта

- Разрешено ли активировать tenant до подтверждения owner? Требования говорят, что tenant до provision владельца не полностью подготовлен, но текущий `PENDING → ACTIVE` проверяет только settings и plan.
- Полная матрица статусов identity/membership, переходы и время отзыва доступа; сроки хранения приглашений, сессий и аудита.
- Как обрабатывается смена slug после создания tenant-role и кто может запускать отдельное переименование кода.
