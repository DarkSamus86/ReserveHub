# ReserveHub — отчёт backend security review

**Дата:** 2026-10-23  
**Область:** `auth-service`, защита gRPC `tenant-service`, инфраструктура `compose.yaml`.  
**Метод:** статический анализ текущего кода и конфигурации; проверка unit-тестами. Не проводились пентест работающего стенда, проверка Docker-хоста извне и тестирование PostgreSQL/NATS под нагрузкой.  
**Статус:** выводы относятся к состоянию рабочего дерева на момент ревью. BS-05 исправлена после ревью; остальные находки остаются открытыми.

## Краткий вывод

Для локального MVP в доверенной среде есть базовые меры защиты: bcrypt для паролей, проверка подписи и срока JWT, запрет публичного выбора роли `admin`, fail-closed доступ обычного пользователя к tenant RPC. **Текущий Compose не следует публиковать как production-окружение:** он открывает порты без транспортного шифрования и использует общий DB-аккаунт между сервисами.

Уровень риска ниже отражает потенциальное влияние и условия эксплуатации. Публикация портов Compose сама по себе не доказывает доступность хоста из интернета: это зависит от firewall, сети и окружения развёртывания.

## Находки

### BS-01 · High при доступности портов вне доверенной сети · HTTP/gRPC без TLS и опубликованные сервисы

**Подтверждение:** `auth-service` запускает обычный HTTP через `ListenAndServe` (`services/auth-service/cmd/auth-service/main.go:60–71`), в том числе для login с паролем и ответа с bearer token (`services/auth-service/internal/httpapi/handler.go:50–61`). `tenant-service` слушает gRPC без TLS (`services/tenant-service/cmd/tenant-service/main.go:71–82`). Compose публикует auth HTTP, tenant gRPC, PostgreSQL и NATS на портах хоста (`compose.yaml:15–46,91–107,148–167`).

**Риск:** при перехвате трафика раскрываются пароль или токен; прямой доступ к PostgreSQL/NATS расширяет поверхность атаки.

**Рекомендация:** в production разрешать внешний доступ только через TLS-терминирующий gateway, закрыть прямые публикации PostgreSQL/NATS и внутренних RPC; для локального запуска при необходимости привязывать опубликованные порты к `127.0.0.1`. Защитить сервисные соединения внутри недоверенной сети.

### BS-02 · High · Одинаковые полномочия БД у разных сервисов

**Подтверждение:** PostgreSQL создаётся с одним пользователем и паролем (по умолчанию `reservehub:reservehub`); обе строки подключения для auth и tenant используют эти же credentials (`compose.yaml:19–21,99–100,157–159`). Схемы в одном PostgreSQL разграничены именами, но не отдельными DB users.

**Риск:** компрометация одного сервиса даёт доступ к данным другой схемы; пароль по умолчанию опасен при опубликованном порту.

**Рекомендация:** отдельные уникальные учётные записи БД для auth и tenant, права только на свою схему/таблицы, отдельные права для миграций; убрать предсказуемые production-пароли и не публиковать PostgreSQL наружу.

### BS-03 · High · Общий симметричный секрет JWT у issuer и verifier

**Подтверждение:** `AUTH_JWT_SECRET` передаётся и `auth-service`, и `tenant-service` (`compose.yaml:103,164`). Auth подписывает HS256 (`services/auth-service/internal/auth/token.go:32–48`), tenant проверяет тем же секретом (`services/tenant-service/internal/authn/token.go:32–64`).

**Риск:** утечка секрета в любом сервисе-проверяющем позволяет подписать поддельный токен с ролью `admin`.

**Рекомендация:** перейти на асимметричную подпись: приватный ключ только в auth-service, публичный ключ у проверяющих сервисов; предусмотреть `kid`, ротацию ключей и проверку audience. До миграции обеспечить строгое хранение общего секрета.

### BS-04 · High · Нет rate limiting на публичных endpoint-ах аутентификации

**Подтверждение:** `/v1/auth/register` и `/v1/auth/login` доступны без предварительной аутентификации (`services/auth-service/internal/httpapi/handler.go:18–28`). Каждый валидный запрос регистрации вычисляет bcrypt-хэш, а login сравнивает пароль с bcrypt-хэшем (`services/auth-service/internal/auth/service.go:63–94`). Ограничение размера одного JSON-запроса (`services/auth-service/internal/httpapi/handler.go:99–109`) не ограничивает частоту запросов.

**Риск:** перебор паролей, массовое создание аккаунтов и истощение CPU.

**Рекомендация:** лимиты на gateway и в сервисе по IP, аккаунту и маршруту; backoff для неудачных попыток, мониторинг аномалий, ограничения конкурентной работы bcrypt. Не строить политику только на IP за общими прокси.

### BS-05 · Medium · Bootstrap администратора повторно устанавливал пароль при рестарте — исправлено

**На момент ревью:** при наличии `AUTH_BOOTSTRAP_ADMIN_EMAIL` startup всегда вызывал `BootstrapAdmin`, а SQL `ON CONFLICT (email) DO UPDATE` перезаписывал password hash и роль.

**Риск:** позднейшая смена пароля могла быть незаметно отменена рестартом, пока bootstrap credentials оставались в окружении.

**Исправление:** создание администратора вынесено в отдельный одноразовый Compose job после миграций; репозиторий делает insert без обновления существующих аккаунтов и проверяет наличие admin под транзакционной блокировкой. Повторный запуск не сбрасывает пароль и не повышает обычного пользователя до admin. Bootstrap credentials следует удалить после начальной настройки; ротация пароля требует отдельной явной операции с аудитом.

### BS-06 · Medium · Нет досрочного отзыва access token и проверки актуальности роли

**Подтверждение:** auth выдаёт JWT на 15 минут (`services/auth-service/internal/config/config.go:18–26`), а tenant принимает подписанную роль из токена без запроса текущего состояния пользователя (`services/tenant-service/internal/authn/interceptor.go:20–31`). Logout, revocation и блокировка аккаунта отсутствуют в текущем auth API (`services/auth-service/internal/httpapi/handler.go:18–28`).

**Риск:** токен продолжает работать до истечения TTL даже после необходимости срочно отозвать административный доступ или компрометации токена.

**Рекомендация:** ввести серверные сессии/отзыв, версию токена или актуальной роли и политику немедленного отзыва для критичных административных операций; документировать максимально допустимое окно задержки.

### BS-07 · Medium · gRPC reflection не защищён unary interceptor

**Подтверждение:** сервер настраивает `grpc.ChainUnaryInterceptor`, но не stream interceptor, и включает `reflection.Register` (`services/tenant-service/cmd/tenant-service/main.go:75–89`). gRPC reflection использует streaming RPC, следовательно unary-проверка JWT его не перехватывает.

**Риск:** без токена можно получить схему/описания доступных методов. Это информационная утечка, а не обход авторизации unary-методов tenant-service.

**Рекомендация:** отключать reflection вне локальной разработки либо добавить stream interceptor с аналогичной политикой доступа и тестом на вызов без токена.

### BS-08 · Medium/Low · Определение существования аккаунта

**Подтверждение:** повторная регистрация отвечает `409 email_taken` (`services/auth-service/internal/httpapi/handler.go:86–95`). При login для отсутствующего email возврат происходит без bcrypt-проверки, а для существующего — после неё (`services/auth-service/internal/auth/service.go:82–94`).

**Риск:** различие ответа регистрации и задержки входа помогает перечислять email зарегистрированных пользователей.

**Рекомендация:** оценить требования приватности; для login уравнять обработку отсутствующего пользователя фиктивной bcrypt-проверкой, сочетая с rate limiting. При необходимости сделать внешний ответ регистрации менее информативным.

### BS-09 · Medium при использовании логов как аудита · Недоверенный tenant ID и request ID в gRPC-логах

**Подтверждение:** метрики и логирование выполняются внешним interceptor до проверки JWT (`services/tenant-service/cmd/tenant-service/main.go:76–82`); `tenant_id` записывается прямо из входящего запроса (`services/tenant-service/internal/observability/metrics.go:40–71`). Входящий `x-request-id` принимается без проверки длины/формата (`services/tenant-service/internal/observability/metrics.go:76–80`). В отличие от этого, auth HTTP проверяет формат request ID (`services/auth-service/internal/httpapi/logging.go:40–51`).

**Риск:** отклонённый запрос может создать запись с подложным tenant ID или чрезмерно большим request ID; такой лог нельзя считать достоверным аудитом.

**Рекомендация:** записывать отдельное поле для заявленного клиентом tenant ID либо доверенный `tenant_id` только после проверки прав; ограничить формат и длину gRPC request ID.

## Положительные меры в текущем коде

- Публичная регистрация принудительно создаёт роль `user`; выбор `admin` клиентом не предусмотрен (`services/auth-service/internal/auth/service.go:63–79`).
- Пароль хэшируется bcrypt, валидируется длина 12–72 байта (`services/auth-service/internal/auth/service.go:63–74,147–152`).
- JWT проверяется по HS256-подписи, issuer, сроку действия и допустимым глобальным ролям (`services/auth-service/internal/auth/token.go:51–83`, `services/tenant-service/internal/authn/token.go:32–64`).
- `user` без tenant membership закрыт от tenant RPC по умолчанию (`services/tenant-service/internal/authn/interceptor.go:24–31`).
- SQL-запросы используют параметры, а HTTP request logging не записывает body и Authorization header (`services/auth-service/internal/repository/postgres.go`, `services/auth-service/internal/httpapi/logging.go:12–37`).

## Рекомендуемый порядок исправления

1. Закрыть внешние порты БД/NATS и прямой auth/tenant-доступ; включить TLS и сменить дефолтные credentials.
2. Разделить DB users и права схем; убрать общий HMAC signing secret из сервисов-проверяющих.
3. Ввести rate limiting login/register; перезапись admin-пароля bootstrap-процессом уже устранена.
4. Защитить/выключить reflection, добавить отзыв токенов и ограничить доверие к пользовательским полям в логах.
5. Проверить защищённый стенд динамическими тестами: попытки без токена, перебор, повреждённые JWT, межtenant-доступ, Docker network/firewall и миграции БД.

## Проверки и ограничения отчёта

`go test ./...` выполнен в `services/auth-service` и `services/tenant-service`, обе команды прошли. Эти тесты не подтверждают безопасность сети, реальные права PostgreSQL, работу миграций или устойчивость под нагрузкой. Код в ходе security review и оформления отчёта не изменялся.
