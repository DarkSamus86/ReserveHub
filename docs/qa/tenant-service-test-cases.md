# Тест-кейсы: tenant-service

Основа: [Tenant Service Specification](../services/tenant-service/ReserveHub-Tenant-Service-Full-Specification.md), §22, §30 (в частности BR-004 и BR-006) и §43 (MVP); интеграция с auth — [Auth STPO](../services/auth-service/ReserveHub-Auth-Service-STPO.md), этапы A–C. Актуальные статусы — в [регрессионном отчёте](./test-results-2026-10-23-regression.md); [предыдущий прогон](./test-results-2026-10-23.md) сохранён для истории. Изменяющие данные проверки запускать в изолированной временной БД/схеме и удалять тестовые ресурсы.

| ID | Сценарий / шаги | Ожидаемый результат | Приоритет |
| --- | --- | --- | --- |
| TEN-01 | Вызвать health check, затем `GetTenant` без токена и с валидным user-токеном. | Health `SERVING`; RPC без токена `Unauthenticated`, user `PermissionDenied`. | P0 |
| TEN-02 | Вызвать tenant RPC с валидным platform admin token, неверной подписью и истёкшим token. | Admin допущен до бизнес-обработки; неверный/истёкший токен `Unauthenticated`. | P0 |
| TEN-03 | Создать tenant с уникальным slug, планом и настройками; прочитать и найти в списке. Повторить slug. | Статус `PENDING`, связанные данные и outbox в одной транзакции; slug уникален, конфликт не создаёт дубликат. | P0 |
| TEN-04 | Активировать tenant без настроек/действующего плана; затем с обоими условиями. | Без необходимых условий `FailedPrecondition`; с ними `ACTIVE`, событие outbox. | P0 |
| TEN-05 | Пройти `PENDING → ACTIVE → SUSPENDED → ACTIVE → ARCHIVED`; проверить запрещённые переходы и запись после архивации. | Допустимые переходы выполняются, недопустимые отклоняются, архив не редактируется. | P0 |
| TEN-06 | На `SUSPENDED` обновить tenant, настройки, branding, домен, план, лимит и фичу от лица администратора. Дополнительно проверить прямой вызов repository и гонку с приостановкой. | По BR-004 tenant-specific writes запрещены во всех путях записи. | P1 |
| TEN-07 | Получить лимит/фичу тарифа; установить и убрать override. | Приоритет override над тарифом, после удаления возврат к значениям плана; превышение лимита доменов отклонено. | P0 |
| TEN-08 | Сменить план на будущий момент T2, затем назначить другой на более ранний T1 < T2; проверить историю/активные интервалы после T2. Повторить с уже прошедшими T1/T2. | На каждый момент действует ровно один тариф; история состоявшихся назначений не удаляется (BR-006). Политика отмены будущего назначения требует решения продукта и аудита. | P1 |
| TEN-09 | Добавить домен; НЕ размещать DNS/HTTP доказательство владения; отправить токен, возвращённый API, в `VerifyTenantDomain`. | Статус не должен стать `VERIFIED` без независимой проверки владения доменом; primary недоступен. | P1 |
| TEN-10 | Добавить домен с корректным proof, проверить, назначить primary, затем отключить. | `VERIFIED`, только один primary в tenant, disabled не остаётся primary; события отражены в outbox. | P1 |
| TEN-11 | Два tenant: запрос данных первого с membership второго; поменять `tenant_id` в запросе. | Только своё членство и разрешённые действия; чужие данные недоступны. | P0, этапы B–C (пока нет membership) |
| TEN-12 | После `CreateTenant` проверить создание владельца в auth и доступ к своей компании; повторить событие после сбоя. | Владелец/tenant-role/membership provision один раз; до готовности owner tenant не считается полностью подготовленным. | P0, этап B (пока нет реализации) |
| TEN-13 | Прочитать outbox после серии успешных/отклонённых операций. | По успешным событиям записи присутствуют; при откате нет события и частично записанных данных. | P1 |
| TEN-14 | Попросить gRPC reflection без токена в окружении, отличном от локального. | Reflection отключён либо защищён, если политика окружения запрещает анонимное перечисление методов. | P2 |

Тесты TEN-09/10 требуют определиться с источником proof (DNS TXT/HTTP), но **возвращённый из API токен сам по себе не является доказательством владения**. Для TEN-08 требуется определить, сохраняется ли будущее назначение после более ранней смены либо явно отменяется с записью в аудит; уже состоявшуюся историю удалять нельзя.
