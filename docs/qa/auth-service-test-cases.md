# Тест-кейсы: auth-service

Основа: [Auth STPO](../services/auth-service/ReserveHub-Auth-Service-STPO.md), §9–10; текущий этап A отделён от будущих этапов B–D. Актуальные статусы и доказательства — в [регрессионном отчёте](./test-results-2026-10-23-regression.md); [предыдущий прогон](./test-results-2026-10-23.md) сохранён для истории. Секреты, пароли и access token нельзя помещать в отчёты/логи. Для изменяющих БД тестов использовать отдельную временную БД, не общую dev-БД.

| ID | Сценарий / шаги | Ожидаемый результат | Приоритет |
| --- | --- | --- | --- |
| AUTH-01 | Запустить миграции на пустой БД, выполнить `bootstrap-admin` с уникальными email и паролем, войти и вызвать `/v1/auth/me`. | Миграции создают роли, bootstrap создаёт одного platform admin; login 200, `/me` 200 с ролью `admin`. | P0 |
| AUTH-02 | Повторить bootstrap без credentials; затем с другими credentials; повторить вход со старым паролем. | Успех без изменения email, роли и password hash; новый пароль не заменяет старый. | P0 |
| AUTH-03 | На пустой БД вызвать bootstrap без credentials. | Ошибка и неуспешный запуск сервера; нет admin с известным паролем по умолчанию. | P0 |
| AUTH-04 | При отсутствии admin создать обычного user с тем же email, что указан для bootstrap. | Bootstrap не повышает user до admin и не меняет пароль; явная ошибка. | P0 |
| AUTH-05 | Зарегистрироваться с email в смешанном регистре и допустимым паролем; войти email в нижнем регистре, вызвать `/me`. | Регистрация 201, email нормализован, роль `user`, вход и `/me` 200; в БД только bcrypt hash. | P0 |
| AUTH-06 | Повторно зарегистрировать тот же email; попробовать некорректный email и пароль короче 12 байт. | Повтор 409; невалидный ввод 400; записи пользователя не дублируются. | P1 |
| AUTH-07 | Неверный пароль/несуществующий email; `/me` без bearer, с повреждённым/истёкшим токеном. | 401, профиль не выдан; токен без правильной подписи или с истёкшим сроком не принимается. | P0 |
| AUTH-08 | Проверить HTTP-запрос с нестандартным `X-Request-ID`, пароль и bearer в теле/заголовках при логировании. | Стабильная JSON-схема, безопасный request ID, пароль/email/token не попадают в access log. | P1 |
| AUTH-09 | С platform admin и обычным user выполнить защищённый `GetTenant` для несуществующего UUID. | Admin проходит авторизацию (`NotFound` из бизнес-слоя); user получает `PermissionDenied`; без токена `Unauthenticated`. | P0 |
| AUTH-10 | В изолированной БД присвоить user роль с `scope=tenant`, `code=admin`, получить токен и вызвать RPC другого tenant; отдельно проверить platform admin и токен без `scope`. | Tenant-scoped `admin` получает `PermissionDenied`; platform admin допущен; токен без `scope` отклонён. | P0, до этапа B |
| AUTH-11 | Создать tenant, повторно доставить событие создания, создать/пригласить владельца и роль `{tenant_slug}`. | Одна identity и membership, нет дубликатов, owner ограничен своим tenant; повтор после ошибки безопасен. | P0, этап B (пока нет реализации) |
| AUTH-12 | Сменить роль/заблокировать admin с уже выданным токеном; проверить RPC до истечения токена. | В зависимости от согласованной политики немедленный отзыв либо явно документированное окно задержки (сейчас до 15 минут). | P1, этап D |
| AUTH-13 | Проверить refresh/logout/reset/rate limiting и защиту от brute force. | Сессия отзывается/ротируется; злоупотребления ограничены; отсутствие утечки данных. | P1, этап D (пока нет реализации) |

Для AUTH-10 требуется **только временная БД и управляемая SQL-фикстура**: публичный API не позволяет назначать роли. Не применять такую фикстуру к рабочим данным.
