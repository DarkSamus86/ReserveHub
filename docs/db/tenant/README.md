# Tenant Service: план развития БД

**Состояние:** предложения для текущей ветки `dev`, 2026-10-23; миграции и код этим документом не меняются.
**Основание:** [полная спецификация Tenant](../../services/tenant-service/ReserveHub-Tenant-Service-Full-Specification.md), [исходная DB-спецификация](../tenant_db/ReserveHub-Tenant-Service-Database-Agent-Spec.md), [регресс QA](../../qa/test-results-2026-10-23-regression.md), миграции `services/tenant-service/migrations/000001–000020` и `internal/repository/*`. Бизнес-инварианты сверены с `analyst`. Этот документ дополняет существующую DB-спецификацию, без повторного описания всех таблиц.

## Граница и подтверждённое состояние

`tenant-service` — источник истины для lifecycle, settings, domain, branding, тарифов, лимитов, features и outbox. Пользователи, пароль, membership и приглашения принадлежат `auth-service`. `CreateTenant` сейчас в одной транзакции создаёт `PENDING`, settings, branding, начальное назначение тарифа и `tenant.created` в outbox. Provision первого владельца — отдельный идемпотентный межсервисный процесс, без общей SQL-транзакции.

Текущая топология — один PostgreSQL database `reservehub`, две схемы `auth_service` и `tenant_service`. Ближайший шаг — разные runtime/migration DB roles и права по схемам без межсхемных FK и JOIN в приложении. Отдельные database или кластеры можно рассмотреть позже для независимого масштабирования/восстановления; это не требуется для исправления нынешних инвариантов и потребует миграции данных и перепроверки межсервисных контрактов.

Действующие уникальные ограничения защищают slug (`md_tenant`), домен глобально (`md_tenant_domain`) и максимум один primary домен на tenant. `hs_tenant_plan_assignment` и override-таблицы проверяют лишь положительную длину периода; непересечение не ограничено. `ChangePlan` удаляет назначения начиная с `effective_from`, включая уже состоявшиеся при ретроактивном вызове: QA воспроизвёл потерю истории **TEN-08 / BR-006**. `VerifyDomain` сравнивает переданный RPC токен с токеном, возвращённым API, без DNS/HTTP proof: **TEN-09**. Guard для `SUSPENDED` стоит до транзакции на уровне application, а repository допускает прямую запись и гонку с приостановкой: **TEN-06, остаточный риск**. Это текущие блокеры бизнес-корректности, а не готовые ограничения БД.

## Что делать сейчас

### 1. Защитить историю тарифов

До решения продукта прекратить физическое удаление строк `hs_tenant_plan_assignment` при обычном `ChangePlan`; как минимум исключить удаление уже начавшихся назначений. Для запланированных будущих назначений нужен статус отмены/замены и audit record, если продукт разрешит их изменять. `GetPlanHistory` должен сохранять исходные назначения и отражать отмену; `GetCurrentPlan` учитывает только действующие интервалы. Не применять backfill, который угадывает удалённую историю: восстановить её можно лишь из надёжных backup/журналов, и отчёт QA не доказывает, что такие данные есть.

После выбора политики будущих/ретроактивных изменений обеспечить однозначность плана в каждый момент. Предлагается `EXCLUDE USING gist (tenant_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)` на **действующих** периодах; для UUID нужен `btree_gist`. Если отменённые назначения остаются в той же таблице, constraint должен иметь predicate по статусу действующих назначений, а `GetCurrentPlan` — тот же фильтр. Иначе отменённая строка пересечётся с заменой; альтернативой служит отдельная audit-таблица для отменённых записей. Перед добавлением ограничения проверить существующие пересечения и согласовать исправление. Нулевая/отрицательная длина уже запрещена. Индекс поиска текущего плана пересмотреть по реальному плану запроса после constraint, не дублировать без измерения. Все изменения одного tenant сериализовать блокировкой строки `md_tenant FOR UPDATE` (или другим согласованным per-tenant lock) в транзакции; `FOR UPDATE` одной найденной строки assignment не защищает от конкурентной вставки. В одной транзакции менять интервалы, сохранять audit/событие и вставлять outbox; при конфликте constraint переводить SQL-ошибку в доменную.

### 2. Согласовать `SUSPENDED` с записью

Для каждой tenant-specific write-операции repository в начале транзакции читать и блокировать `md_tenant` по `tenant_id FOR UPDATE`, затем проверять статус. `ChangeTenantState` уже блокирует ту же строку: это даёт определённый порядок commit между suspend и записью. Все пути записи, включая settings, branding, plan, overrides, domain и будущие операции, должны использовать один helper/контракт; проверка application до `BEGIN` остаётся удобной ошибкой, но не гарантией целостности. Операции изменения статуса требуют отдельной матрицы исключений; например, возобновление из `SUSPENDED` должно оставаться возможным. DB trigger как второй рубеж обсуждать только после определения полного набора таблиц и исключений, иначе он сломает законные административные операции.

`ARCHIVED` — логическая архивация. Миграции дочерних таблиц содержат `ON DELETE CASCADE`, в том числе у тарифной истории. Поэтому runtime DB role не должна иметь `DELETE` на `md_tenant` и истории; прямое физическое удаление грозит потерей данных. Политику retention/позднего hard delete определить отдельно, с backup и аудитом. Пересмотреть `RemoveLimitOverride`/`RemoveFeatureOverride`: сейчас они физически удаляют записи overrides, что затрудняет историческую реконструкцию effective entitlements.

### 3. Подтверждать домен внешним proof

В `md_tenant_domain` хранить состояние challenge (`PENDING`, expiry, попытки), метод proof, дату проверки и минимальные сведения о результате. Токен challenge может быть показан владельцу для размещения DNS TXT или HTTP файла, но **повторная передача этого токена в RPC не является proof**. Независимый verifier выполняет DNS/HTTP проверку и только доверенная серверная операция переводит в `VERIFIED`, проставляет `verified_at` и пишет outbox в той же транзакции. Хранить полный DNS/HTTP ответ и секреты без необходимости не следует. При повторной проверке/смене владельца домена нужна политика истечения доказательства.

Существующий partial unique index обеспечивает максимум один primary домен, но `primary ⇒ VERIFIED` проверяет лишь код репозитория. После перехода на доверенный verifier можно добавить DB trigger или ограничить право обновления status/primary отдельной DB ролью; простой `CHECK` с FK на справочник не проверит статус `VERIFIED` по другой таблице. Выбрать вариант вместе с `backend-security` и покрыть конкурентную смену primary. Глобальная уникальность `domain` есть, но нормализацию IDN/case/trailing dot и повторное использование `DISABLED` домена надо определить до изменения уникального ключа.

### 4. Разделить права и сохранить доставку событий

В Compose оба сервиса, bootstrap и migrator используют один PostgreSQL user; `search_path=tenant_service` не является изоляцией. Создать отдельные runtime/migration роли tenant и auth: runtime tenant получает только нужные DML права на свою схему, без DDL и без доступа к `auth_service`; migrator — DDL только своей схемы. Права на extension `pgcrypto` в `public` готовит отдельный setup шаг с повышенными полномочиями, а не runtime. Проверить права текущих и будущих таблиц, default privileges, `search_path`, TLS для недоверенной сети и закрытие DB-порта.

Outbox уже пишется в тех же транзакциях, что business rows. Publisher читает `published_at IS NULL ORDER BY created_at,id LIMIT 100` и отмечает отправку после NATS; между publish и mark возможна повторная доставка. Получатели должны быть идемпотентны по `event_id`. Если будет несколько publisher workers, согласовать lease/`SKIP LOCKED` и recovery до параллельного запуска. В старой DB-спецификации встречается `tenant.domain.added`, тогда как service spec и текущий код используют `tenant.domain.created`; контракт события надо закрепить как `tenant.domain.created`, не выпускать оба имени без версии.

## Owner provisioning: межсервисный контракт

Tenant transaction фиксирует `tenant.created` и идентификатор tenant; оркестратор/consumer вызывает защищённый idempotent provision Auth по `tenant_id`, стабильному slug и email владельца, переданному только в защищённом provisioning-контексте. Не класть email/пароль в широковещательный `tenant.created`. Состояние процесса (`requested`, `retryable_failure`, `completed`, без чувствительных деталей ошибки) должно быть наблюдаемым; где оно живёт, определить с владельцем оркестратора. Ошибка Auth не откатывает уже созданный tenant. Повторная доставка не создаёт вторую identity/role/membership. `tenant.slug` допускает 100 символов и может начинаться с цифры, а `auth_service.roles.code` — 63 и требует начальную букву: до включения provisioning согласовать предел/отображение. При изменении slug код роли автоматически не меняется.

## Порядок миграций и проверка

1. Совместно с `backend-security` утвердить контракт repository: транзакционный status lock, порядок блокировок, события, SQL-ошибки и поведение старой версии приложения. Не менять миграции `000001–000020`; добавлять новые после `000020`.
2. На копии данных read-only аудит пересечений планов, удалённых/осиротевших записей, статусов доменов, runtime grants и длительности запросов. Для больших таблиц планировать создание индексов и validation отдельно, учесть блокировки DDL. Новый constraint вводить только после очистки данных и развёртывания совместимого кода.
3. Сделать backup и проверить восстановление. Down для нового ограничения обычно возможен; отмена кода/миграции не вернёт физически удалённые назначения или proof, которого не было. Восстановление истории — из проверенного backup/audit, а не синтетический backfill.
4. Приёмка: `SUSPENDED` после commit не допускает новых tenant writes даже при конкурентном suspend; archive сохраняет строки; в любой момент максимум один активный план и прошлая история не исчезает; `VERIFIED`/primary возможны только после внешнего proof; outbox и business row атомарны; runtime tenant не может читать/писать auth schema и удалять `md_tenant`.

## Открытые решения продукта

- Допускаются ли ретроактивные назначения тарифов и как корректировать уже прошедшую историю? При замене будущего назначения требуется отмена с аудитом или сохранение прежнего расписания? До ответа не кодировать спорную политику в constraint/миграции.
- Можно ли перевести `PENDING → ACTIVE` до подтверждения первого owner? Какие tenant-specific операции разрешены в `SUSPENDED` и какие чтения разрешены в `ARCHIVED`?
- Сроки хранения domain proof, plan/audit/outbox и override history; порядок освобождения домена и slug после архивации; период и способ подтверждения владения доменом.
